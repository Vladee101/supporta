# Runbook

Операционные сценарии Support-агента. Каждый алерт из
[deploy/prometheus/alerts.yml](../deploy/prometheus/alerts.yml) ссылается на свой
раздел (`runbook_url`). Runbook ведётся вместе с кодом, а не в отдельной вики:
меняется поведение - в том же коммите меняется и раздел (митигация риска по ADR-003).

Общее для всех сценариев:

- **trace_id** - сквозной идентификатор: заголовок `X-Trace-Id` ответа API, поле
  `trace_id` в теле ошибки, в `audit_log`, в событии outbox и в строках JSON-лога API
  и consumer'а (поллер публикует события пачками, его строки без trace_id). Начинать разбор с него: `GET /api/v1/tickets/{id}/audit` показывает
  все решения по тикету.
- **Postgres - источник истины** (ADR-004). RabbitMQ - транспорт: потерянное сообщение
  восстанавливается из outbox, обратное неверно.
- Логи в JSON (`LOG_FORMAT=json`), персональные данные в них уже замаскированы тем же
  редактором, что стоит перед LLM.

<a id="outbox-stalled"></a>
## Поллер встал: OutboxStalled, OutboxStuckEvents

**Что значит.** Событие эскалации записано в `outbox_events` вместе с тикетом, но
больше 2 минут не опубликовано в RabbitMQ. Оператор эскалацию не видит, хотя клиенту
уже ответили «передано специалисту».

**Проверить.**

1. Процесс `app.workers.outbox_poller` жив? В логах - строки `database unavailable` /
   `broker connection lost` с нарастающей паузой: воркер пережидает сбой сам
   (`app/workers/backoff.py`), перезапуск не нужен, если инфраструктура поднимается.
2. `support_rabbitmq_up` и `support_database_up` на `/metrics`.
3. Застрявшие события: `SELECT id, attempts, last_error FROM outbox_events WHERE NOT published ORDER BY created_at;`

**Что делать.**

- Поллер не запущен или упал - запустить: `python -m app.workers.outbox_poller`.
  Он подберёт все накопленные события, дублей не будет: consumer отсекает повторы по
  `idempotency_key` (inbox `consumed_events`).
- `OutboxStuckEvents`: у события исчерпано `MAX_ATTEMPTS` (10) попыток, поллер его
  больше не берёт. Причина - в `last_error`. После устранения причины вернуть событие
  в работу: `UPDATE outbox_events SET attempts = 0 WHERE id = '<id>';`

<a id="dead-letter"></a>
## Сообщение в DLX: DeadLetterNotEmpty

**Что значит.** Consumer отклонил сообщение без повтора: битый payload, эскалации нет
в базе или неизвестная ошибка. Эскалация в консоль не попала.

**Проверить.** Сообщения в `escalations.dead` (RabbitMQ management, :15672): `message_id`
- это `idempotency_key`, в теле - `escalation_id`, `ticket_id`, `trace_id`. Логи consumer'а
по этому `trace_id`: строка `poison message → DLX` или `unexpected error → DLX` с причиной.

**Что делать.**

- Эскалация в базе есть, причина устранена (например, выкачена правка consumer'а) -
  переложить сообщение обратно в `escalations.created` (shovel или «Move messages» в
  management UI). Повторная доставка безопасна - inbox отсечёт уже обработанное.
- Эскалации в базе нет - сообщение-сирота; удалить после разбора.
- Ни в коем случае не очищать DLX без разбора: это единственный след потерянной эскалации.

<a id="llm-unavailable"></a>
## LLM-провайдер недоступен: LlmUnavailableHigh

**Что значит.** Больше 5% тикетов за 15 минут эскалировано с причиной
`llm_unavailable`: провайдер не ответил после трёх повторов в пределах 10 с (NFR6).
Клиенты не страдают - их тикеты у операторов, - но очередь растёт.

**Проверить.**

1. Логи API: `LLM недоступен, тикет ... эскалирован` и причина от адаптера (таймаут,
   HTTP 429/5xx, сетевая ошибка).
2. Статус провайдера. Для RouterAI и других агрегаторов - и статус исходного провайдера.
3. Сеть: соединение с провайдером должно быть прямым. Через HTTP-прокси установка
   TLS-соединения занимала до 50 с (замер ADR-009) - это съедает весь бюджет NFR1.

**Что делать.** Предупредить старшего смены о росте очереди. Переключение на другую
модель - настройками `LLM_CLASSIFY_MODEL` / `LLM_GENERATE_MODEL` и перезапуском API, но
только на модель, для которой откалиброваны пороги (ADR-009, ADR-012).

<a id="auto-answer-share"></a>
## Доля автоответов вне коридора: AutoAnswerShareLow, AutoAnswerShareHigh

**Что значит.** Ожидаемая доля - около 16% (golden set, текущая конфигурация).
Падение ниже 5% - агент перестал находить ответы: деградация RAG. Рост выше 40% -
агент отвечает там, где раньше эскалировал: подозрение на поломку порогов.

**Проверить.**

- Распределение по правилам: `sum by (rule_id) (increase(support_tickets_processed_total[1h]))`.
  Рост R6/R8 (низкий RAG) при падении R4 - это поиск.
- Недавние изменения базы знаний (консоль → «База знаний», история версий): документ
  удалён или переписан? Индексация отстала - версии без embedding в поиске не участвуют.
- Смена embedding-модели или LLM без перекалибровки порогов - частая причина обоих
  алертов: косинусная шкала не переносится между моделями.

**Что делать.**

- Деградация после обновления KB - восстановить прошлый текст документа новой версией
  (консоль → «База знаний»: история версий хранит все тексты, ADR-011) и дождаться
  индексации.
- Сменилась модель - перекалибровать: `python -m scripts.calibrate_rag --provider bge`
  и прогон `scripts.eval` на golden set (раздел «Confidence и пороги»).

<a id="decision-table-gap"></a>
## Сработало R-default: DecisionTableGap

**Что значит.** Комбинация входов Decision Engine не покрыта ни одним правилом.
Тикет безопасно эскалирован (R-default → A2), но это дефект decision table: полный
перебор 144 комбинаций в тестах такого не допускает, значит, во вход попало значение,
которого таблица не знает (новая категория, новый источник confidence).

**Что делать.** Найти тикет по `audit_log.rule_id = 'R-default'`, воспроизвести вход в
`tests/test_decision_engine.py`, добавить правило в таблицу design document и в
`app/domain/decision.py` - в одном коммите, с тестом.

<a id="auto-answer-latency"></a>
## Медленные автоответы: AutoAnswerLatencyHigh

**Что значит.** p95 обработки тикета, закончившегося автоответом, выше 8 с (NFR1).

**Проверить.** Задержку провайдера (`support_llm_calls_total` против времени), пул
потоков API (`API_WORKER_THREADS`) и пул соединений с базой (`DB_POOL_SIZE`) - нагрузочный
тест нашёл, что именно они упираются первыми (reports/nfr_report.md).

<a id="llm-cost"></a>
## Стоимость LLM: LlmCostPerTicketHigh, LlmCostUnknown

**Что значит.** Средняя стоимость на тикет за сутки выше порога NFR5 ($0.02 ≈ 1.68 ₽;
замер - 0.1 ₽). Или провайдер перестал сообщать стоимость, и контроль NFR5 слепой.

**Проверить.** `llm_usage` в `audit_log` дорогих тикетов: число вызовов (повторы по
NFR6 и k-sampling умножают стоимость), токены (выросший промпт генерации), модель.
Частая причина - `LLM_K_SAMPLES` > 1 без нужды (ADR-012) или смена модели на более дорогую.

---

<a id="operator-override"></a>
## Растёт доля правок оператора: OperatorOverrideRateGrowth

**Что значит.** Операторы всё чаще переписывают черновики агента. Не авария, а сигнал
качества: черновики расходятся с тем, что считают правильным люди.

**Проверить.** Сходство черновика и ответа оператора в `audit_log` по правкам за неделю,
категории и документы KB, на которых строились такие черновики. Разобрать с командой
поддержки и обновить базу знаний.

---

<a id="metrics-source-down"></a>
## Метрики состояния не снимаются: MetricsSourceDown

**Что значит.** `/metrics` отвечает, но не видит Postgres или RabbitMQ. В этот момент
алерты на outbox и DLX слепы - считать их неизвестными, а не зелёными. Разбор - как
недоступность соответствующего сервиса; воркеры пережидают её сами.

---

<a id="api-down"></a>
## API не отвечает: SupportApiDown

**Что значит.** Prometheus не может опросить `/metrics`: процесс API не работает или
недоступен по сети. Приём тикетов остановлен. Проверить процесс, логи запуска и
доступность порта; после рестарта убедиться, что `/health` отвечает.
